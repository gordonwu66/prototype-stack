# System Design - AI-native app prototype
Fundamental web app and agent harness backend with similar features to other AI apps, in order to explore and prototype different services and features.

# Requirements
Basic starting AI web app stack

## Functional
- Web UI for agent chat interface with basic text input, tools/tasks and response output
- Agent session management (CRUD)
- (Stretch) User auth
- (Stretch) Agent personas and creation with isolated docs/files
- (Stretch) Agent usage/token management
- (Stretch) Agent monitoring evals, session history, and tool call observability

## Non-functional
- Real-time agent chat tools/tasks over Socket.IO (WebSocket)
- Async agent harness runtime handling multiple client requests, including longer running or background jobs
- LLM gateway for fronteir and open weight

# Data Entities
- chat_sessions
    - id uuid primary key (generated by the client for a new chat; created on its first message)
    - user_id text not null
    - title text (first message, truncated to 60 chars; renamable)
    - created_at timestamptz not null default now()
    - create index on chat_sessions (user_id, created_at desc)
- chat_messages
    - id bigint generated always as identity
    - session_id uuid not null references chat_sessions(id) on delete cascade
    - turn_id bigserial not null,
    - role text not null check (role in ('user', 'assistant', 'tool'))
    - content jsonb
        - array: [text, tool_use, tool_result, thinking, etc.]
    - model text
    - timestamp timestamptz not null default now()

- agents
    - id uuid primary key default uuidv7()
    - name text
    - description text
    - user_id text not null
- agent_docs/files
    - id uuid primary key default uuidv7()
    - agent_id uuid not null references agents(id) on delete cascade
    - title text
    - content text
    - userId text not null
- users (Clerk)


# API
REST (`apps/api/src/api/chat/routes.py`, `main.py`). No auth yet; later every call carries `authorization: bearer <token>`.
- GET /sessions: newest first
- PUT /sessions/{id} `{title}`: rename
- DELETE /sessions/{id}: also cancels the session's in-flight reply
- No POST /sessions: the first `chat:send` with a new session id creates the session
- GET /models

Chat runs over Socket.IO (below). `chat:send` replaces `POST /chat` and takes the same body:
    {
        session_id: uuid,
        input: text,
        model: text,
        effort: text,
    }



# Chat streaming (Socket.IO)
```
Browser (Chat component, socket.io-client, WebSocket only)
   │  session:join / chat:send / chat:cancel   (acked)
   ▼
FastAPI + python-socketio (mounted at /socket.io)
   │  one asyncio task per in-flight reply, keyed by session
   ▼
LLM gateway  ──► AnthropicProvider        (anthropic SDK, Messages API)
             ──► OpenAIResponsesProvider  (openai SDK, Responses API, store=false)
             ──► OpenAICompatibleProvider (openai SDK, Chat Completions)
                   └─ open-weight: Ollama / vLLM / LM Studio / Fireworks / Groq / Together / OpenRouter
```

- **Protocol** (`apps/api/src/api/chat/socket.py`). Every request carries `session_id`:
    - `session:join {session_id}` → `{session, messages}`. Watches that session and leaves any other; an unknown id is a draft (`session: null`).
    - `chat:send {session_id, input, model, effort}`: creates the session on its first message, then streams a reply.
    - `chat:cancel {session_id}`
- **Session room** (every tab watching the session):
    - `chat:message`: a whole message; clients insert or replace it by id (user prompt, empty assistant placeholder, final assistant message)
    - `chat:delta`: `{session_id, id, seq, kind: "text" | "reasoning", text}`
- **Broadcast to every client** (sidebars): `session:upserted` (created or renamed) and `session:deleted`. Once there are users, these go to a per-user room.
- **Frontend routes:** `/` is the marketing landing page. `/chat` is a new chat; the first send navigates to `/chat/{session_id}`. The sidebar and the single Socket.IO connection live in the `/chat` layout.
- **Resume:** on every (re)connect the client re-joins and gets a history snapshot. Each message carries `seq` (deltas applied), so deltas already in the snapshot are skipped.
- **Cancel:** `chat:cancel` cancels the session's task, which closes the upstream HTTP stream; the partial reply is kept with `stop_reason: "cancelled"`.
- **Gateway** (`apps/api/src/api/llm/`): providers stream provider-neutral events (`TextDelta`, `ReasoningDelta`, `StreamEnd`). Model ids are `<provider>/<model>`; `GET /models` lists those whose provider is configured. History is stored as plain text, so a session can switch models between turns.
    - Anthropic: adaptive thinking with summarized display (streamed as reasoning), `effort` → `output_config.effort`, server-side refusal fallback on Opus/Sonnet.
    - OpenAI: Responses API, stateless (`store: false`; the backend owns history). `effort` → `reasoning.effort`; reasoning summaries (`summary: "auto"`) stream as reasoning.
    - Open-weight: reasoning read from the non-standard `reasoning` / `reasoning_content` delta fields.
- **Storage:** in-memory for now (`ChatStore`); it maps onto `chat_sessions` / `chat_messages`. Moving to Postgres plus Socket.IO's Redis manager is what allows running more than one API process.
